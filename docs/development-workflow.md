# 기능 추가·수정·삭제 워크플로우

이 문서는 Gatekeeper의 모든 기능 변경에 적용합니다. 공통 원칙은 [AGENTS.md](../AGENTS.md), 패키지·검증 명령은 [검증 메모](../agent_memories/repo/verification-notes.md), Git 포인터 순서는 [저장소 메모](../agent_memories/repo/repository-workflow.md)를 따릅니다. 이 문서는 작업의 범위·순서·완료 조건을 정의합니다.

## 1. 작업 단위와 기록

하나의 작업은 사용자가 확인할 수 있는 하나의 결과를 목표로 합니다. UI와 API가 함께 바뀌더라도 같은 결과를 위한 변경이면 하나의 작업으로 추적하고, 저장소별 변경과 검증을 구분합니다. 관련 없는 리팩터링·패키지 업데이트는 별도 작업으로 남깁니다.

작업 시작 시 다음을 짧게 정의합니다.

- 유형: 추가 / 수정 / 삭제 / 동작을 유지하는 리팩터링. 혼합 변경이면 주 유형과 부수 변경을 명시합니다.
- 목적과 현재 → 목표 동작: 누가, 어떤 조건에서, 무엇을 경험해야 하는지 설명합니다.
- 범위와 제외 사항: 영향받는 저장소·모듈·설정·데이터, 이번에 다루지 않는 항목을 명시합니다.
- 수용 기준: 입력·권한·조작에 따른 기대 결과와 실패 결과를 관찰 가능한 문장으로 작성합니다.
- 호환성·버전 영향, 구현 순서, 검증 방법, 남은 결정 사항을 기록합니다.

단순 문구·오타·국소적인 수정은 작업 응답에 이 정보를 요약하면 됩니다. 여러 모듈·저장소에 걸치거나 공개 계약·인증·데이터·배포에 영향이 있으면 [작업 템플릿](../agent_memories/templates/change-template.md)을 사용해 `agent_memories/NN-topic-name/change.md`에 기록하고 [인덱스](../agent_memories/README.md)에 등록합니다. 기존 이슈·작업 기록이 있으면 같은 결과를 위한 별도 기록을 중복 생성하지 말고 연결합니다. 작업 기록을 만들었다는 이유로 GitHub 이슈나 PR을 자동 생성하지 않습니다.

## 2. 상태와 전환 조건

작업 기록의 `Stage`는 아래 순서로 갱신합니다. 공유 메모리의 `Status`는 기록 상태이며, 구현 진행 상태와 구분합니다.

1. `scoping`: 요구·현행 동작·영향 조사 중입니다. 의도를 추측해야 하는 부분을 구분합니다.
2. `ready`: 수용 기준, 범위, 계약·데이터 영향, 검증 방법이 정해져 해당 범위의 구현을 시작할 수 있습니다.
3. `implementing`: 구현과 필요한 테스트·문서 수정을 진행합니다. 범위나 공개 동작이 달라지면 관련 기준을 먼저 갱신합니다.
4. `verifying`: 최종 변경을 기준으로 수용 기준과 필수 검증을 확인합니다. 실패하면 `implementing`으로 돌아가 수정하고 영향받는 검증을 다시 실행합니다.
5. `verified-local`: 수용 기준과 해당 범위의 필수 검증이 충족되었습니다. 커밋·푸시·배포 여부를 별도로 보고합니다.
6. `published`: 요청된 커밋·푸시·병합 범위가 완료되고 원격 커밋 및 필요한 루트 포인터를 확인했습니다. 어떤 범위까지 공개했는지 기록합니다. 배포 완료를 의미하지 않습니다.
7. `released`: 요청 범위의 GitHub Release가 최종 main SHA에 게시되었고 태그·버전·URL을 검증했습니다. 서비스 배포 확인과 dev 복귀 상태는 별도로 기록합니다.
8. `deployed`: 배포가 요청되어 실제 배포 대상과 배포된 커밋, 환경 검증까지 확인했습니다. 소스 변경 작업에서 필수 단계는 아닙니다. 배포 요청의 종료 조건에는 릴리즈 및 최신 dev 복귀도 포함합니다.

필수 검증을 실행할 수 없다면 `verified-local`로 올리지 않고 `verifying`에 유지하며, 메모리 `Status: blocked`와 차단 사유·재개 조건을 기록합니다. 재개하면 `Status: active`로 갱신합니다. 일부 구현이 끝났다는 이유로 전체 완료를 선언하지 않습니다. 로컬 수정만 요청받았다면 `verified-local`에서 `Status: resolved`로 마칠 수 있습니다. 취소된 작업은 `Status: resolved`와 `Outcome: cancelled`를 명시하고 구현 완료와 구분합니다.

`ready`는 별도의 사용자 승인 단계가 아닙니다. 기존 코드로 결정 가능한 구현 선택은 자율적으로 진행합니다. 제품 동작의 상충, 공개 계약 파괴 여부, 데이터 보존·삭제 의도처럼 결과가 달라지는 불확실성만 구체적으로 질문하고, 답변이 필요 없는 조사·검증은 계속합니다. 답이 없다는 이유로 승인된 것으로 간주하지 않습니다.

## 3. 조사와 계약 확정

먼저 루트 지침·공유 메모리·하위 지침을 읽고 각 저장소의 기존 변경을 확인합니다. 현재 작업과 이전 작업의 변경을 구분하며, 기존 작업을 초기화하거나 임의로 묶어 커밋하지 않습니다. 새 작업은 최신 `dev`에서 `feat/<topic>`을 생성해 시작합니다. 기존 진행 작업은 보존합니다. GitHub 조작은 `gh` CLI를 사용하고, [브랜치·릴리즈 절차](github-release-workflow.md)를 따릅니다.

변경 진입점부터 실제 사용처까지 `rg`와 소스 읽기로 추적합니다. 해당하지 않는 항목은 이유를 기록합니다.

- 백엔드: controller/route → DTO·guard → service → repository/entity·migration → cache·스케줄러·metrics.
- 프론트엔드: route/component → auth state·API wrapper → response decoder/type → 로딩·오류·빈 상태·키보드 동작.
- 교차 영향: HTTP method/path/status, 요청·응답 필드와 nullable/optional 의미, 권한·namespace·owner 범위, 페이지네이션, 오류 형식, 환경 변수·기본값, 브라우저 저장 상태.
- 사용처: import/export·DI 등록·라우트 맵·외부 SDK·문서·예제·테스트·운영 설정. 저장소 검색만으로 외부 소비자가 없다고 단정하지 않습니다.

두 앱이 연동되면 변경 전·후 계약과 이전 클라이언트/서버 조합의 동작을 기록합니다. 기존 DTO와 런타임 디코더가 일치하는지 확인하며, 공통 로컬 패키지가 없는 현재 구조에서 공유 모듈을 임의로 만들지 않습니다. 파괴적 변경은 전환 기간·업데이트 순서·복구 방법을 먼저 정합니다.

## 4. 유형별 구현 순서

### 기능 추가

1. 허용·거부 조건과 성공·실패 응답을 정의하고 기존 기능과 중복되는지 확인합니다.
2. 필요할 때 새 migration·설정과 service를 추가한 뒤 DTO·guard·controller로 기능을 노출합니다. 스키마 변경 없이 UI만 바꾸는 작업에 불필요한 백엔드 계층을 만들지 않습니다.
3. 프론트엔드 type/decoder/API helper를 계약에 맞추고 상태와 UI를 연결합니다. 서버 전용 기능이면 프론트엔드 변경은 생략하고 이유를 기록합니다.
4. 정상 흐름뿐 아니라 잘못된 입력·권한 거부·빈 결과·중복 실행·실패 복구·접근성 중 관련 조건을 검증하고 사용자 문서·설정 예제를 갱신합니다.

### 기존 기능 수정

1. 현재 동작을 재현하고 결함 수정인지 의도된 동작 변경인지 구분합니다. 재현하지 못했다면 가설과 확인 방법을 명시합니다.
2. 의미 있는 동작 변경에는 기존 문제를 포착하는 회귀 테스트를 추가합니다. 가능하면 수정 전 실패를 확인하고, 불가능하면 이유를 남깁니다. 단순 문구 수정 등에 구현을 그대로 복제하는 테스트를 만들지 않습니다.
3. 원인이 있는 계층에서 수정하고, 계약이 바뀌는 경우 양쪽 소비자와 문서를 함께 수정합니다. 테스트 기대값만 바꿔 기존 결함을 숨기지 않습니다.
4. 바뀐 조건과 인접한 기존 동작, 인증·비동기 상태·캐시 무효화 등 영향을 확인합니다. 호환성 영향에 맞춰 버전 수준을 판단합니다.

### 기능 삭제

1. 제거할 공개 진입점과 내부 구현, 사용처, 보존할 데이터·감사 기록·설정을 구분합니다. UI에서 숨기는 것인지 API 제공까지 종료하는 것인지 분명히 합니다.
2. 소비자를 먼저 전환합니다. 외부 소비자·롤링 배포·구버전 클라이언트가 있으면 호환 경로와 폐기 일정을 정하고 단계적으로 제거합니다. 소비자가 없다는 증거가 있으면 즉시 제거할 수 있습니다.
3. route·controller·service·DI/module 등록·export·UI·decoder/type·캐시·스케줄러·설정 예제·의존성·문서를 실제 사용 관계에 따라 정리합니다. 다른 기능이 공유하는 코드는 유지합니다. 적용된 migration은 삭제·재작성하지 않습니다.
4. 제거된 기능을 활성 상태로 설명하는 테스트·문서를 정리하고, 공개 진입점을 폐기했다면 의도한 미제공 응답을 검증합니다. 더 이상 접근할 수 없어야 하는 경로·버튼·권한 및 남은 기능의 정상 동작을 확인합니다.
5. 데이터 보존 정책이 정해지지 않으면 데이터와 복구 수단을 유지합니다. 기능 삭제 요청을 운영 데이터 삭제·컬럼 즉시 drop·키 일괄 폐기 권한으로 확대하지 않습니다. 필요한 파괴적 정리는 별도 범위·migration·복구 계획을 기록합니다.

### 구조 개선·리팩터링

외부 동작·계약을 유지한다는 기준을 먼저 세우고 책임 분리·중복 제거·의존 방향 개선처럼 확인할 수 있는 목적을 정합니다. 기존 회귀 검증을 유지하고, 공개 동작 변경이 필요해지면 유형과 수용 기준을 갱신합니다. 파일 수·추상화 수가 늘었다는 이유로 품질 향상을 주장하지 않습니다.

## 5. 구현·배포 의존 순서

구현 검토는 계약 정의 → 데이터·제공자 → 소비자 → 통합 검증 순서로 진행합니다. 로컬에서 함께 수정할 수 있지만 각 중간 상태가 배포 가능한지는 별도로 판단합니다.

- 추가·호환 변경: 필요한 확장 migration/백엔드 제공자를 준비하고 소비 프론트엔드를 연결합니다. 새로운 필드를 기존 데이터에서 처리할 수 있어야 합니다.
- 삭제·비호환 변경: 호환 기능 제공 → 소비자 전환 → 구버전 사용 종료 확인 → 기존 API/스키마 제거 순서로 나눕니다. DB 축소 작업은 이전 바이너리로 단순 롤백할 수 있다고 가정하지 않습니다.
- Git 공개 순서: 실제 변경된 외부 공유 라이브러리 → 소비 앱 각각 → 원격 SHA 확인 → 루트 포인터 순서입니다. 구현 순서·커밋 의존 순서·운영 배포 순서를 혼동하지 않습니다.

버전 수준과 `npm i` → `npm ci` → lockfile·검증 → 자식 커밋/푸시 → 루트 포인터 절차는 AGENTS.md 4–7절을 그대로 적용합니다. 이번 변경이 루트 문서에만 있으면 앱 버전이나 설치를 변경하지 않습니다. 기능 구현 요청만으로 외부 패키지 게시·운영 배포·데이터 파기를 수행하지 않습니다.

사용자가 배포를 요청하면 [GitHub·릴리즈 절차](github-release-workflow.md)에 따라 앱별 `feat/* → dev → main`, 앱 Release, 루트 포인터의 동일한 PR 승격, 프로젝트 범위의 루트 조합 Release까지 수행합니다. 이후 main을 dev에 동기화하고 로컬 dev와 의존성을 최신화합니다. 원격 보호 규칙·필수 검증은 생략하지 않습니다.

## 6. 검증과 완료 판정

수용 기준마다 검증 근거를 대응시킵니다. 결과는 `pass`, `fail`, `blocked`, `not-run`, `not-applicable`로 기록하고 실패·미실행·제외 이유를 남깁니다. 자동 테스트·mock 검증·실제 서비스 검증을 구분합니다.

- 변경한 앱은 AGENTS.md의 lint·타입·테스트·build 게이트를 통과해야 합니다. 공유 프론트엔드 런타임·설정 변경은 Cloudflare/Node 빌드를 모두 확인합니다.
- 인증·권한 변경은 허용과 거부, 소유자/namespace 경계, 만료·로그아웃·중복 요청을 확인합니다. UI 변경은 관련 로딩·오류·빈 상태와 키보드·포커스를 확인합니다.
- 프록시·캐시·수명주기·스키마 변경은 해당 통합 검증을 수행합니다. 프록시 변경은 벤치마크 조건을 기록하며, 짧은 smoke 결과로 성능 향상을 단정하지 않습니다.
- 의존성 변경은 두 audit 범위와 설치 호환성을 확인합니다. 외부 인프라가 필요한 검증을 mock 통과로 대체했다고 주장하지 않습니다.
- 최종 관련 수정 이후 유효한 검사 결과를 사용합니다. 코드 수정 후 영향받는 검사를 다시 실행하고, 문서만 수정했다면 링크·경로·공백 검증만 갱신합니다. 검증 근거가 유효한 무관한 검사를 반복하지 않습니다.

로컬 완료 체크리스트:

- [ ] 수용 기준을 충족하고 관련 기존 동작을 유지한다.
- [ ] 미사용 등록·export·설정·문서가 남아 있지 않고 새 계약의 양쪽 구현이 일치한다.
- [ ] 필요한 회귀 테스트·수동 검증과 최종 패키지/lockfile 게이트가 통과했다.
